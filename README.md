# Nano Banana — Gemini app vs Interactions API

Compares multi-turn image editing with Nano Banana in the **Gemini app** against the same
edit chains run through the **Gemini API** (multi-turn editing with the Interactions API,
chaining each turn on the previous interaction id). The API chains are run with
**Nano Banana 2** (`gemini-3.1-flash-image`, high thinking level, at 2K and 1K output)
and **Nano Banana Pro** (`gemini-3-pro-image`, 2K output).

## The problem (for the Gemini team)

Multi-turn editing progressively degrades image quality in **both** the Gemini app and
the API: with every edit the whole image is re-generated and detail is lost turn after
turn. But the two paths do not degrade the same way — starting from the same image and
applying the same 10 edit prompts, the API results come out **noticeably worse** than
what the Gemini app produces, even at 2K with high thinking level.

We would like to understand:

- what the Gemini app does differently from a plain Interactions API chain
  (model variant, resolution, prompt rewriting, internal pipeline, …);
- how the API should be used to obtain results at least as good as the app — and
  ideally how to do multi-turn editing with **no quality reduction at all** across turns.

The original Gemini app conversations for the two experiments:

- **Exp 1 — woman in the living room:** <https://share.gemini.google/Fdu4vPhYBGX1>
- **Exp 2 — fruits:** <https://share.gemini.google/ErsX4RwvL0JF>

## Experiments

Two experiments, each a chain of 10 edits applied to the same starting image
(generated in the Gemini app):

- **Exp 1** — living-room scene, 10 heterogeneous edits (color change, object
  add/remove, material change, spatial move, background, lighting, …)
- **Exp 2** — fruit still life, 10 additive edits (one fruit per turn)

Each experiment is re-run through the Interactions API in these configurations:

| Notebook                  | Model (API)                              | Output size | Results directories                          |
| ------------------------- | ---------------------------------------- | ----------- | -------------------------------------------- |
| `notebooks/exp1_nb2.ipynb` | Nano Banana 2 (`gemini-3.1-flash-image`) | 2K and 1K   | `data/exp1_api_nb2_2k/`, `data/exp1_api_nb2_1k/` |
| `notebooks/exp1_pro.ipynb` | Nano Banana Pro (`gemini-3-pro-image`)   | 2K          | `data/exp1_api_pro_2k/`                      |
| `notebooks/exp2_nb2.ipynb` | Nano Banana 2 (`gemini-3.1-flash-image`) | 2K and 1K   | `data/exp2_api_nb2_2k/`, `data/exp2_api_nb2_1k/` |
| `notebooks/exp2_pro.ipynb` | Nano Banana Pro (`gemini-3-pro-image`)   | 2K          | `data/exp2_api_pro_2k/`                      |

Nano Banana 2 chains run with `thinking_level: high`; the `thinking_level` control is
not available on Nano Banana Pro (Pro thinks by default and it cannot be disabled).

## Layout

- `data/exp1/`, `data/exp2/` — outputs saved from the Gemini app
  (`0.jpeg` = starting image, `N.jpeg` = result after edit N)
- `data/exp{1,2}_api_nb2_{2k,1k}/`, `data/exp{1,2}_api_pro_2k/` — outputs of the API
  chains, same numbering (generated by the notebooks)
- `notebooks/exp{1,2}_{nb2,pro}.ipynb` — run the API edit chains and render an
  interactive comparison: a slider to pick the turn plus a wipe slider on the image
  (left: Gemini app, right: API)

The comparison widget needs a live notebook frontend (VS Code / Jupyter); GitHub's static
notebook preview won't run it.

## Setup

```sh
uv sync
cp .env.example .env  # then add your Gemini API key
```

Run the notebooks with the project virtualenv (`.venv`) as kernel. A chain whose outputs
are already complete on disk is skipped, so re-running a notebook costs no API calls; to
regenerate a chain, delete its `data/exp*_api_*` directory first. Each turn chains on the
previous interaction id, so a partially generated chain is re-run from turn 1.
